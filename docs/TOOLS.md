# MCP tool reference

The `etim-json` MCP server exposes **five tools**, all read-only, over one
model loaded at startup. This document is the complete contract: schemas,
annotations, behaviour on missing data, and worked request/response pairs.

Server identity: `etim-json` · transport: **stdio** · protocol: MCP
(current spec via `@modelcontextprotocol/sdk`).

Every tool carries the same annotations:

| Annotation | Value | Meaning |
| --- | --- | --- |
| `readOnlyHint` | `true` | Nothing is written, anywhere |
| `destructiveHint` | `false` | No destructive action exists to hint about |
| `idempotentHint` | `true` | Same call, same answer, any number of times |
| `openWorldHint` | `false` | Answers come from the loaded model only — no network, no external state |

When the loaded model is the bundled synthetic demo, every text response is
prefixed `⚠ SYNTHETIC DEMO DATA …` and every structured response carries
`"synthetic": true`. Real conversions carry neither.

All structured responses are validated by the server against the declared
output schema before they are returned — a response that does not match the
schema is a server error, not a silent divergence.

---

## `etim_model_info`

*Describe the loaded ETIM model.* Call once at the start of a session to
learn what you are querying: which release, how many entities, which
languages, and whose data it is.

**Input schema:** no arguments.

**Output schema**

| Field | Type | Notes |
| --- | --- | --- |
| `release` | `string` | e.g. `"ETIM-10.0"`, `"DYNAMIC"`, or `"DEMO-1.0"` |
| `languages` | `string[]` | Translation languages present (English is implicit) |
| `synthetic` | `boolean` | `true` only for the bundled demo |
| `counts` | `object` | `classes`, `groups`, `features`, `values`, `units` — all `number` |
| `attribution` | `string` | The ODC-BY attribution the model carries |

**Example**

```json
// request
{ "name": "etim_model_info", "arguments": {} }

// structuredContent (demo model)
{
  "release": "DEMO-1.0",
  "languages": ["DE"],
  "synthetic": true,
  "counts": { "classes": 3, "groups": 2, "features": 6, "values": 5, "units": 4 },
  "attribution": "SYNTHETIC DEMO DATA generated by etim-json — not the ETIM classification model. …"
}
```

## `etim_search_classes`

*Find ETIM classes* by free text, synonym, translation, or exact code.
Matching is case- and diacritic-insensitive (`Gehäuse` ≡ `gehause`, `ß` ≡
`ss`); results are ranked — exact code, then exact description, then
word-start, substring, synonym, translation — and the ranking is stable
across calls.

**Input schema**

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `query` | `string` | yes | 1–200 chars; text or a class code |
| `groupCode` | `string` | no | `^EG\d{6,8}$` — restrict to one group |
| `language` | `string` | no | 2–5 chars, e.g. `"DE"` — also search that language's translations |
| `limit` | `integer` | no | 1–100, default 20 |

**Output schema**

| Field | Type |
| --- | --- |
| `synthetic` | `boolean` (optional) |
| `total` | `number` |
| `hits[]` | `{ code, description, group, groupCode, version, matched }` |

`matched` names what text matched: `code`, `description`, `synonym` or
`translation`. An empty `hits` array with `total: 0` is the answer for "no
match" — never an error.

**Example**

```json
// request
{ "name": "etim_search_classes",
  "arguments": { "query": "Leitungsschutzschalter", "language": "DE" } }

// structuredContent (demo model)
{
  "synthetic": true,
  "total": 1,
  "hits": [{
    "code": "EC990002", "description": "Demo: miniature circuit breaker",
    "group": "Demo group — switching and protection", "groupCode": "EG990002",
    "version": 1, "matched": "translation"
  }]
}
```

## `etim_get_class`

*One ETIM class in full*: description, group, synonyms, sectors, and every
feature in published order with its type, unit(s) and permitted values —
every code already joined to its vocabulary entry.

**Input schema**

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `code` | `string` | yes | `^EC\d{6,8}$` (case-insensitive) |

A malformed code is rejected at the schema boundary with a message showing
the expected shape. A well-formed code that is not in the model returns
`{ "found": false }` — absence is an answer, not an error.

**Output schema**

| Field | Type |
| --- | --- |
| `synthetic` | `boolean` (optional) |
| `found` | `boolean` |
| `class` | present when `found` — see below |

`class`: `{ code, version, description, group{code,description}, synonyms[],
sectors[], features[] }` where each feature is `{ code, description, type,
orderNumber, unit?, unitImperial?, values[]?, deprecated? }` and units are
`{ code, abbreviation, description }`.

Feature `type` is ETIM's own single letter: `A` alphanumeric (choose from
`values`), `L` logical, `N` numeric (with `unit` where defined), `R` range.

**Example**

```json
// request
{ "name": "etim_get_class", "arguments": { "code": "EC990001" } }

// structuredContent, abridged
{
  "synthetic": true,
  "found": true,
  "class": {
    "code": "EC990001", "version": 3, "description": "Demo: installation cable",
    "group": { "code": "EG990001", "description": "Demo group — cables and accessories" },
    "features": [
      { "code": "EF990001", "type": "N", "orderNumber": 1,
        "description": "Demo: outer diameter",
        "unit": { "code": "EU990001", "abbreviation": "mm", "description": "Demo: millimetre" },
        "unitImperial": { "code": "EU990002", "abbreviation": "in", "description": "Demo: inch" } },
      { "code": "EF990002", "type": "A", "orderNumber": 2,
        "description": "Demo: conductor material",
        "values": [{ "code": "EV990001", "description": "Demo: copper" }] }
    ]
  }
}
```

## `etim_lookup`

*Identify any ETIM code* without knowing its kind: `EC` class, `EG` group,
`EF` feature, `EV` value, `EU` unit. Returns the kind, the description, and
kind-specific detail (a feature reports how many classes use it and lists up
to 25; a group reports its class count; a unit reports its abbreviation).

**Input schema**

| Field | Type | Required | Constraints |
| --- | --- | --- | --- |
| `code` | `string` | yes | `^E[CGFVU]\d{6,8}$` (case-insensitive) |

**Output schema:** `{ synthetic?, found, kind?, code?, description?, detail? }`
— `detail` is an open record whose keys depend on the kind, as above.

**Example**

```json
{ "name": "etim_lookup", "arguments": { "code": "EF990003" } }

// structuredContent
{ "synthetic": true, "found": true, "kind": "feature", "code": "EF990003",
  "description": "Demo: halogen-free",
  "detail": { "type": "L", "usedByClassCount": 3, "usedBy": ["EC990001", "EC990002", "EC990003"] } }
```

## `etim_list_groups`

*The top-level map of the model*: every product group with its class count.
Useful as the first browse step before narrowing a search with `groupCode`.

**Input schema:** no arguments.

**Output schema:** `{ synthetic?, groups: [{ code, description, classCount }] }`,
sorted by code.

## Example prompts

Prompts a connected assistant can answer with these tools:

1. *"Which ETIM class should I use for a miniature circuit breaker, and what
   features does it require?"* → `etim_search_classes` then `etim_get_class`.
2. *"What does EU570448 mean? I keep seeing it in our BMEcat export."* →
   `etim_lookup`.
3. *"List every product group in our ETIM model and how many classes each
   has, so I can see coverage."* → `etim_list_groups`.
4. *"Für 'Kabelverschraubung' — welche ETIM-Klasse, und welche Merkmale hat
   sie?"* → `etim_search_classes` with `language: "DE"`, then
   `etim_get_class`.
5. *"Which release is this server answering from, and is it real data?"* →
   `etim_model_info` (the answer includes the synthetic flag and the
   attribution).

## Error behaviour

| Condition | Behaviour |
| --- | --- |
| Malformed arguments (wrong shape, out of bounds, oversized) | Schema rejection with a corrective message; `isError: true` |
| Well-formed code not present in the model | `{ "found": false }` — a data answer |
| Unknown tool name | JSON-RPC error from the SDK |
| Unparseable frame on stdin | Frame discarded by the transport; server continues serving |

## Operational notes

- The model is loaded and validated **once at startup**; a server that
  started is a server whose data passed referential-integrity checks.
- No tool accepts a filesystem path, URL or credential. The operator chooses
  the dataset; the agent can only query it.
- Memory: a full ETIM release in this format is tens of MB; the loader
  refuses files over 512 MB as hostile.
